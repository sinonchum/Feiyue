# AI递归自我提升现状讨论（2026-06-12）

## 摘要

本次讨论围绕 AI 递归自我提升（Recursive Self-Improvement, RSI）的学术与工程现状展开：重点从早期“AI 自主改写底层源代码导致智能爆炸”的科幻叙事，转向更务实的工程路径——合成数据、自对弈、AI 反馈、推理期自我修正、环境反馈与代码执行，以及多智能体协作。讨论中也强调了一个关键判断：现代 RSI 更像是“反馈闭环 + 自动化评估 + 训练/推理迭代”的系统工程，而不是单个模型无限自我改写。

## 核心要点

- **合成数据与自对弈**：STaR、SPIN、RLAIF 等方法通过模型生成、筛选、评价数据，绕开人类高质量数据耗尽的问题。
- **推理期自我修正**：Reflexion、Self-Refine、MCTS / Tree Search 等方法让模型在生成过程中进行反思、搜索和剪枝。
- **环境驱动进化**：代码编译、测试、运行环境、游戏或模拟器等提供真实 Ground Truth，是更可靠的自我改进信号。
- **Agent 与多智能体协作**：单模型自我循环容易坍塌，多角色、多模型、外部评估器和工具调用能形成更稳健的闭环。
- **现实边界**：当前前沿更接近“工程化自我迭代”和“局部能力提升”，尚未等同于失控式通用智能爆炸。

这是关于rsi学术界的声音：关于AI的递归自我提升（Recursive Self-Improvement, RSI）和自我迭代，学术界目前的态度已经从早期的“科幻式”（AI自主修改底层源代码来实现智能爆炸）转向了高度务实和工程化的方向。
​目前学术界最优秀的做法主要集中在如何让模型利用自身能力生成、筛选高质量反馈，从而在不需要人类干预的情况下实现性能的螺旋上升。以下是目前学术界最务实、也最前沿的几个核心方向：
​1. 基于合成数据与自对弈（Self-Play & Synthetic Data）
​由于人类产生的高质量高质量数据即将耗尽（Data Wall），让AI自己教自己成为了最务实的方向。这在强化学习中早已被证明（如AlphaZero），目前正广泛应用于大语言模型（LLM）。
​STaR (Self-Taught Reasoner): 斯坦福和谷歌提出的经典方法。模型先尝试解答数学或逻辑题，如果最终答案正确，就把中间的推理过程（Rationale）加入训练集微调自己；如果错误，则让模型借助正确答案重新推导。这实现了推理能力的自我引导。
​SPIN (Self-Play Fine-Tuning): UCLA提出的自我博弈微调。模型扮演两个角色：一个是生成数据的“自己”，一个是辨别自身生成数据与人类高质量数据差异的“裁判”。通过这种对抗，模型不断逼近甚至超越原始人类数据的质量。
​RLAIF (Reinforcement Learning from AI Feedback): 用强大的AI（如GPT-4）代替人类标注员，为模型的输出打分并生成奖励模型。这是目前大厂和学术界都在大规模使用的低成本迭代方式。
​2. 推理期的自我反思与修正（Inference-Time Self-Correction）
​不在底层权重上动刀，而是在模型生成结果时引入“系统2（System 2）”的慢思考机制，让模型自我检查。
​Reflexion / Self-Refine: 让模型在输出初稿后，根据环境反馈（比如代码编译报错信息，或者另一套Prompt生成的评估标准）写出一段“反思（Reflection）”，然后基于反思修改输出。
​结合蒙特卡洛树搜索（MCTS）: 类似AlphaGo的搜索机制。在推理时，让LLM生成多个可能的后续步骤，并通过自身的评估函数（Value Model）对这些分支进行打分和剪枝。谷歌的 AlphaGeometry 和近期引发热议的 Q-Star (Q)* 传闻方向，都是将LLM与树搜索结合，实现逻辑能力的自我迭代。
​3. 环境驱动的代码与策略进化（Environment-Driven Evolution）
​学术界认为，真正的RSI需要AI能够与环境交互并获得真实的反馈信号（Ground Truth），而编写代码并在真实环境中运行是最好的闭环。
​Eureka (Nvidia & 宾大): 这是一个非常典型的RSI应用。传统的机器人强化学习需要人类专家苦思冥想设计奖励函数（Reward Function）。Eureka让LLM根据环境代码自动写奖励函数，放到模拟器里跑，根据跑出来的效果（反馈），LLM再自动修改和迭代奖励函数，最终实现了超越人类专家设计的强化学习效果。
​Voyager (Nvidia 等): 在《我的世界》（Minecraft）中，AI不断编写控制角色的代码技能，如果执行失败，它会读取环境报错并自我修正代码，然后将成功的代码存入“技能库”供未来调用。
​4. 自动机器学习与元提示优化（AutoML & Meta-Optimization）
​让模型自动优化驱动自己的“控制指令”或“架构参数”。
​OPRO (Optimization by PROmpting): 谷歌提出的方法，用大模型来优化大模型的Prompt。模型根据历史Prompt的得分表现，自动总结规律，生成一批新的、可能得分更高的新Prompt进行测试，实现了Prompt指令的自动化自我迭代。
​The AI Scientist (Sakana AI 等近期工作): 这是向完全自动化科研迈出的一步。系统利用LLM自主提出研究假设、编写实验代码、执行实验、分析结果，甚至自己写出完整的学术论文，并由另一个LLM扮演审稿人进行评审和打回修改。虽然目前生成的成果还比较初步，但这已经是RSI在科研维度的雏形。
​⚠️ 学术界目前面临的核心挑战（务实的瓶颈）
​尽管上述方向前景广阔，但学术界在追求RSI时也达成了几个共识，这些也是目前亟待解决的瓶颈：
​模型崩溃（Model Collapse）： 如果一个模型持续不断地只用自己生成的数据训练自己，几代之后，它的输出多样性会急剧下降，甚至变成只输出无意义的乱码。解决办法通常是必须保留一定比例的真实世界数据作为“锚点”。
​奖励作弊（Reward Hacking）： 当AI自己评估自己时，它很容易找到捷径。比如为了在自我评估中拿高分，它会生成看起来很漂亮但实际上逻辑不通的“幻觉”过程。因此，寻找外部的客观验证源（如代码编译器、数学定理证明器 Lean 等）至关重要。

- 自评估/互评
- 外部环境反馈

## 1. 这更像“工程化自举”，不是强 RSI

你这段里提到的 STaR、SPIN、RLAIF、Reflexion、Eureka、Voyager、OPRO、AI Scientist，确实都属于“模型参与改进自身系统表现”的方向。

但严格说，它们大多不是强意义上的 RSI：

- **不是模型自主修改自身底层架构**
- **不是持续在线更新自身权重**
- **不是无监督无限提升**
- **通常依赖外部训练管线、人类预设任务、验证器或环境反馈**
- **提升范围多半限定在某类任务：数学、代码、机器人奖励、游戏技能、prompt 优化等**

所以更准确的说法是：

> 当前学术界的 RSI 已经从“AI 改写自己导致智能爆炸”的宏大叙事，收缩为“在受控任务环境中，通过模型生成候选、模型/工具评估、外部验证反馈、再训练或再搜索，形成局部能力提升闭环”。

这个表述更学术、也更不容易被质疑。

## 2. 最重要的分界：有没有外部 Ground Truth

这段里最关键的判断是对的：**真正有效的自我提升，往往需要外部可验证信号**。

我会把这些方法按可靠性排序：

### A. 最可靠：外部客观验证器

例如：

- 代码：编译器、单元测试、运行结果
- 数学：定理证明器、Lean、Coq、形式验证器
- 游戏/机器人：模拟器 reward、环境状态
- 搜索任务：已知答案、可验证目标

代表：

- Eureka
- Voyager
- AlphaGeometry
- 代码 agent 的 self-debug loop
- theorem proving + LLM

这类最接近务实 RSI，因为模型不是“相信自己”，而是被环境纠错。

### B. 次可靠：强模型当 judge / reward model

例如：

- RLAIF
- Constitutional AI
- LLM-as-a-judge
- Self-Rewarding Language Models

这类可以规模化，但风险是：

- judge 偏差
- reward hacking
- 偏好模型被投机
- 生成“看起来合理”的答案，而不是真的正确

### C. 最不可靠：纯 self-reflection

例如：

- “请你检查自己的答案”
- “反思一下再改”
- 没有外部反馈的 Self-Refine

这类在很多任务上有用，但不是稳定提升机制。尤其当模型第一次就不知道错在哪里时，它的“反思”也可能只是更自信的幻觉。

一句话：

> 无外部反馈的自我修正，更多是采样和重写技巧；有环境反馈的自我修正，才更像真正的自我迭代。

## 3. 文中几个点可以更严谨

### STaR

你的描述基本准确。STaR 的核心是：

- 模型生成 reasoning rationale
- 正确答案的 rationale 被加入训练
- 错误样本可借助正确答案 rationalize
- 通过迭代微调提升推理能力

但它依赖“最终答案是否正确”的监督信号，所以不是完全自发。

### SPIN

方向对。SPIN 的重点是 self-play fine-tuning，把模型自己生成的数据和人类数据/高质量数据区分开，通过类似对抗训练的形式让模型逼近目标分布。

可以补一句：

> SPIN 的本质不是模型凭空创造真理，而是利用“区分人类/模型数据”的训练信号，让模型分布逐渐接近甚至超越初始 SFT 数据分布。

### RLAIF

这里要小心：RLAIF 不一定是“模型自己评价自己”。很多时候是：

- 一个更强模型评价较弱模型
- 一个固定的 AI preference model 打分
- 或者用宪法规则/原则生成偏好反馈

所以它更准确叫：

> 用 AI 反馈替代或扩展人类偏好反馈，而不是严格意义上的自我反馈。

### MCTS / Q-Star

MCTS + LLM 是重要方向，但你文里的 “Q-Star 传闻” 建议弱化。因为 Q* 不是正式学术结果，最好不要和 AlphaGeometry、MCTS 并列为学术证据。

更稳妥写法：

> LLM + tree search / verifier / value model 是非常明确的研究方向；至于 Q*，公开信息不足，更适合作为工业界传闻而非学术依据。

### AlphaGeometry

AlphaGeometry 的确体现了“语言模型生成候选 + 符号系统验证/搜索”的路线，但它不是普通意义上 LLM 自我迭代，而是：

- 神经模型生成辅助构造
- 符号推理引擎验证和推进证明
- 合成数据训练几何证明模型

所以它支持你的论点，但最好归到“神经-符号搜索 + 外部验证器”，而不是简单说“LLM 自我迭代”。

### AI Scientist

这个方向很重要，但要加保守 caveat：

- 目前自动科研系统能跑通完整 loop
- 但生成成果质量、novelty、实验可靠性、审稿可信度还有限
- 更像“自动化科研助理/实验工厂”的雏形，而不是成熟科学家替代品

## 4. 可以补充几个前沿方向

如果你想让这段更完整，可以加这几类。

### 过程监督 / verifier-guided reasoning

不仅看最终答案，还评价中间步骤：

- process reward model
- verifier model
- step-level search
- best-of-N / tree-of-thought / graph-of-thought
- test-time compute scaling

这和 RSI 关系很大，因为模型提升不一定来自训练，而可能来自**推理时搜索更深**。

核心思想：

> 不改模型，也能靠更多候选生成、验证器筛选、搜索策略优化来提高能力。

### Self-Rewarding / LLM-as-Judge 自训练

有一类工作让模型同时提升：

- response generator
- reward model / judge

这比普通 RLAIF 更接近“自我提升”，但也更容易 reward hacking。

关键风险是：

> 如果 judge 和 generator 同源、同偏差，系统可能会越来越会讨好自己的评分器，而不是真正更正确。

### 合成数据过滤比合成数据生成更关键

现在大家越来越意识到：

> 生成 synthetic data 不难，难的是筛掉坏数据。

高质量自举一般需要：

- 多模型交叉验证
- 执行验证
- 去重
- 难度分层
- 反例构造
- 保留真实数据 anchor
- 防止模式坍塌

所以“AI 自己教自己”的核心不是“生成更多数据”，而是“生成后能否可靠筛选”。

## 5. 这段最值得强调的瓶颈

你已经提到两个核心瓶颈：model collapse 和 reward hacking。还可以补三个。

### 评估污染

如果模型生成训练数据时已经见过 benchmark，提升可能是假象。

尤其是数学、代码、问答榜单，很容易出现：

- benchmark leakage
- prompt overfitting
- judge overfitting
- synthetic data 记忆化

### 分布收缩

即使没有乱码式 collapse，模型也可能变得：

- 更模板化
- 更自信
- 更少探索
- 风格更单一
- 对边缘问题更差

这比“输出乱码”的 model collapse 更常见、更隐蔽。

### 自我评估的不可校准性

LLM 对自己答案的置信度经常不可靠。它可以很好地解释自己为什么对，但不一定知道自己是否真的对。

所以目前共识基本是：

> LLM 可以生成候选和解释，但最终评价最好交给外部环境、形式系统、测试集、强验证器或独立 judge。

## 6. 我会把这段改成一个更锋利的结论

可以这样总结：

> 学术界当前最务实的 RSI，不是“AI 修改自身源码”，而是“模型参与构造训练与推理闭环”：生成候选 → 外部或 AI 评估 → 过滤/搜索/微调 → 再生成。真正有效的系统通常不依赖模型单纯相信自己，而是引入环境反馈、程序执行、形式验证、模拟器、测试集或独立 reward model。换言之，现代 RSI 的关键不在“自我”，而在“闭环”和“可验证反馈”。

这句话我觉得可以作为你这段的核心 thesis。

# 1. 需要几个分工？

我建议最少 **8 个角色**。不是每个角色都必须是一个独立进程，但逻辑上要分开。

## 角色 0：你 —— Creative Director / Founder

你的职责不是写细节，而是提供：

- 原始创意
- 审美铁律
- 产品方向
- 用户场景
- 不能妥协的边界

> 创意由你提出，AI 补全、完善、结构化、执行。

这个很好。不要急着让 AI 替代你的创意源头。系统第一阶段应该做的是：**让 AI 更好地理解、放大、实现你的创意**。

- 风险清单

这个角色不写代码，也不直接下发给弱模型。它负责把你的灵感变成“可被工程理解的方向”。

---

## 角色 2：PRD Author / 产品规格师

推荐模型：

- GPT-5.5
- Gemini 3.1 Pro

输出：

- PRD
- 用户流程
- 功能列表
- 权限需求
- i18n 要求
- 数据结构
- 业务边界
- 验收标准

这个角色要强模型来做，因为 PRD 一旦错，后面弱模型会非常高效地把错误实现出来。

PRD 里必须包含：

```text
1. Goal
2. Non-goals
3. User stories
4. Acceptance criteria
5. i18n requirements
6. Design constraints
7. Technical constraints
8. Verification plan
9. Open questions
```

尤其你的项目要强制写：

- zh/en 从一开始就设计
- 不允许硬编码单语言
- UI 不能出现 gradients/neon/warm yellow
- Android 4dp 圆角，不要大圆角卡片
- Show to Driver / Voyager / MasqueGPS / FRAutoEntrep 等项目-specific rules

---

## 角色 3：Spec Architect / 技术规格架构师

推荐模型：

- GPT-5.5
- Gemini 3.1 Pro

职责：

把 PRD 转成工程 spec。

输出：

- 模块边界
- 文件路径
- API contract
- 数据模型
- 状态流
- 错误处理策略
- 测试策略
- 每个任务的验收条件

这一步非常关键。弱模型不是不能干活，而是它们很怕：

- spec 不完整
- 文件边界不清楚
- 修改范围太大
- 同时要理解产品、架构、代码、测试、审美

所以强模型要把每个任务压成弱模型能执行的“窄任务”。

---

## 角色 4：Planner / 大纲拆解器

推荐模型：

- GPT-5.5 / Gemini 3.1 Pro 做高阶计划
- DeepSeek V4 Pro 可做二级任务拆解
- MiMo / DeepSeek Flash 不建议做总规划

职责：

把 spec 拆成 task contract。

每个 task contract 应该长这样：

```text
Task ID: phase-2-task-3
Title: Add bilingual copy layer for onboarding screen

Scope:
- Modify: app/src/main/...
- Add: app/src/main/...
- Do not touch: navigation graph, theme tokens, API layer

Context:
- Existing language enum path:
- Existing design token path:
- Existing screen file:
- Project rules:

Requirements:
- Add zh/en strings
- No hardcoded Chinese in composable
- Preserve existing font hierarchy
- No gradients/neon/warm yellow

Acceptance Criteria:
- Build passes
- Screen renders in zh and en
- Existing tests pass
- No unrelated diffs

Verification:
- Command 1
- Command 2
- Expected output

Escalation:
- If build fails after 2 attempts, produce bug dossier for teacher.
```

这就是弱模型能稳定执行的单位。

---

## 角色 5：Worker / 执行工人

推荐模型：

- Xiaomi MiMo V2.5 Pro
- DeepSeek V4 Pro
- DeepSeek V4 Flash
- 其他便宜/快模型

职责：

- 根据 task contract 修改代码
- 不重新设计架构
- 不随意扩大范围
- 不自作主张改产品
- 不跳过测试
- 失败时输出 bug dossier

弱模型要被限制成：

> 只做明确任务，不做大脑风暴，不重新解释产品，不发明新需求。

这是让弱模型“变强”的第一步：**不要给它超出能力边界的任务**。

---

## 角色 6：Verifier / 验证器

这个角色最好不是 LLM，而是环境。

包括：

- TypeScript build
- Gradle build
- unit tests
- lint
- Playwright
- adb install + launch
- logcat
- screenshot
- API smoke test
- i18n grep
- no-gradient/no-neon grep
- PR diff check

在 RSI 里，Verifier 是最重要的。  
没有 Verifier，弱模型和强模型都会自嗨。

你的系统应该坚持：

> LLM 自评不能作为完成依据，真实工具输出才是完成依据。

---

## 角色 7：Teacher / 老师

推荐模型：

- GPT-5.5
- Gemini 3.1 Pro

职责：

不是一开始就亲自干活，而是当 worker 卡住时介入。

输入不能是“老师帮我看看”，而应该是标准化 bug dossier：

```text
Bug Dossier

Task:
- phase/task id
- original requirement

Changed files:
- file A
- file B

Failure:
- exact command
- exact error output
- relevant stack trace

Worker attempts:
- attempt 1 summary
- attempt 2 summary
- what was changed

Suspected cause:
- worker's hypothesis

Request to teacher:
- identify root cause
- produce minimal patch strategy
- explain rule that should be remembered
```

老师输出：

- 根因
- 最小修复策略
- 防止复发的规则
- 是否应该更新 skill / spec template / eval

注意：老师最好不要直接把整个任务接管，否则弱模型不会“进化”。  
老师应该优先给“诊断 + 原则 + 局部补丁方案”。

---

## 角色 8：Curator / 经验沉淀员

推荐模型：

- GPT-5.5 / Gemini 用于高质量抽象
- DeepSeek Pro 可做初稿
- Hermes memory + skills 负责持久化

职责：

每次任务完成后，把经验压缩成：

- project-memory
- skill
- checklist
- eval case
- anti-pattern
- prompt patch
- task template patch

这一步就是“自我进化”的核心。

如果不沉淀，系统只是多 agent 外包。  
如果沉淀得好，它才会越来越像 RSI。

# 2. 整体系统拓扑

可以设计成这样：

```text
你：创意 / 方向 / 品味 / 最终判断
        ↓
Strong Planner Lane
GPT-5.5 / Gemini 3.1 Pro
        ↓
PRD → Specs → Task Contracts → Acceptance Gates
        ↓
Hermes Orchestrator
        ↓
Worker Pool
MiMo Pro / DeepSeek Pro / DeepSeek Flash
        ↓
Build / Test / Runtime / Visual / i18n Verifiers
        ↓
失败？
  ├─ 否 → Reviewer → Curator → Skills/Memory/Evals
  └─ 是 → Bug Dossier → Teacher GPT/Gemini → Worker retry
                                      ↓
                            Lesson Extraction
                                      ↓
                         Weak-model task templates improve
```

本质是一个闭环：

```text
创意 → 规格 → 执行 → 验证 → 失败 → 老师纠偏 → 经验沉淀 → 下一次更好
```

这就是你要的“工程化 RSI”。

# 3. Hermes 里怎么落地？

Hermes 本身可以承担四类能力：

## A. Orchestrator 主控

主 Hermes 使用强模型或你当前最可靠模型，负责：

- 接收你的需求
- 调用强模型写 PRD/spec
- 拆任务
- 分派 worker
- 收集结果
- 跑验证
- 决定是否升级到 teacher
- 更新 skills / memory

---

## B. Worker 通过独立 Hermes 进程跑

因为你希望不同模型分工，不能只靠一个 `delegate_task`。更合适的是用独立 Hermes 进程或 profile。

例如逻辑上：

```bash
hermes chat -q "按照 task contract 实现 phase-1-task-2" \
  --provider xiaomi \
  --model Xiaomi-MiMo-V2.5-Pro \
  --toolsets terminal,file
```

或者：

```bash
hermes chat -q "执行这个修复任务..." \
  --provider deepseek \
  --model deepseek-v4-flash \
  --toolsets terminal,file
```

复杂项目建议用 profile：

```text
profile: teacher-gpt
profile: teacher-gemini
profile: worker-mimo
profile: worker-deepseek-pro
profile: worker-deepseek-flash
profile: reviewer
profile: curator
```

每个 profile 可以有自己的：

- 默认模型
- toolsets
- skills
- memory
- cwd
- safety setting

这样更接近“组织分工”。

---

## C. 用 worktree 隔离并行开发

Worker 不应该在同一个工作树里并发改文件。

每个 worker lane 使用：

```bash
hermes -w
```

或者手动 git worktree：

```text
worktree/worker-a
worktree/worker-b
worktree/worker-c
```

规则：

- 一个 worker 一个 branch
- 一个 task 一个 branch
- parent/orchestrator 负责 merge
- merge 后跑集成验证
- worker 不直接 push main

---

## D. Cron / Webhook 做持续自进化

可以用 Hermes cron 做周期性任务：

- 每晚总结当天失败案例
- 每周更新项目 skill
- 每次 PR 合并后生成 regression eval
- 每天跑 smoke tests
- 每周让强模型 review 弱模型失败最多的任务类型

例如：

```text
Nightly Curator:
- 读取本周任务日志
- 找出失败最多的模式
- 生成 lessons.md
- 更新 project-memory.md
- 提议 skill patch
```

这就是低成本持续 RSI。

# 4. “弱模型一同进化”具体怎么实现？

这里要分清楚：  
如果不 fine-tune，弱模型的权重不会变。但系统可以让弱模型**表现上越来越强**。

有五层进化。

---

## 第 1 层：任务模板进化

弱模型失败一次，更新 task contract 模板。

比如它经常忘记 i18n，就把模板加上：

```text
Before editing:
- grep for existing i18n pattern
- identify language enum
- identify copy layer
- do not hardcode user-visible strings

After editing:
- grep for Chinese literals
- grep for English literals
- confirm all UI strings use copy layer
```

这会马上提升弱模型表现。

---

## 第 2 层：项目规则进化

把项目特定规则写入 `.hermes/project-memory.md` 或项目 skill。

例如：

```text
Voyager mobile:
- Always use utils/clerk-hooks.ts
- Never import directly from @clerk/clerk-expo
- RootLayout must only provide providers
- AppContent owns hooks
- Always render Slot
```

之后每个 worker 都收到这些规则，错误率会大幅下降。

---

## 第 3 层：失败案例库进化

每个 bug 都应该转成 eval case。

例如：

```text
Case: Worker imported @clerk/clerk-expo directly
Detection:
- grep -rn "@clerk/clerk-expo" app/
Expected:
- no direct imports except utils/clerk-hooks.ts
Fix:
- route all Clerk access through utils/clerk-hooks.ts
```

以后 worker 交付后自动跑：

```bash
grep -rn "@clerk/clerk-expo" app/
```

这样弱模型不用真的“理解变强”，系统也会防住它。

---

## 第 4 层：教师反馈蒸馏

Teacher 每次救火后，不只是修 bug，还要产出：

```text
Teacher Lesson:
- Symptom:
- Root cause:
- General rule:
- Detection command:
- Prevention prompt:
- Template patch:
```

然后 Curator 把它写进：

- skill
- task template
- preflight checklist
- verifier script

这就是“老师能力迁移给弱模型”。

---

## 第 5 层：可选 fine-tuning / RAG

等你积累到足够多数据后，可以考虑训练或检索增强。

数据格式：

```json
{
  "task_contract": "...",
  "weak_model_attempt": "...",
  "build_error": "...",
  "teacher_diagnosis": "...",
  "final_patch": "...",
  "lesson": "..."
}
```

用途：

- 做 worker prompt few-shot
- 做项目 RAG
- 做小模型 LoRA/SFT
- 做 failure classifier
- 做自动 task router

但第一阶段不建议急着 fine-tune。  
先把流程、数据、验证闭环跑起来。

# 5. 创造性怎么放进这个系统？

你说得很关键：现在创造性主要由你提出，AI 补全和完善。

我建议把“创造性”拆成三层：

## 第一层：Human Seed

你给：

```text
我想做一个 xxx
感觉应该是 xxx
不要像 xxx
用户应该感受到 xxx
视觉上不要 xxx
```

这部分保持由你主导。

---

## 第二层：AI Expansion

强模型做扩展：

- 10 个功能方向
- 5 个风格方向
- 3 个极端用户故事
- 3 个 MVP 版本
- 3 个反常规方案
- 哪些不该做

但强模型不能自己决定。它只提供候选。

---

## 第三层：AI Critic + Human Selection

强模型再做批判：

```text
方案 A：
- 创新度
- 实现成本
- 用户价值
- 品牌一致性
- 风险
- 为什么可能失败

方案 B：
...
```

你选方向。

然后进入 PRD/spec/worker。

也就是说：

```text
你产生原始审美和方向
AI 负责扩展空间
AI 负责批判和结构化
你做最终 taste selection
```

这很适合现在的 AI 能力边界。

# 6. 关键机制：Task Contract

整个系统能不能跑起来，核心不在模型，而在 task contract。

弱模型收到的任务不能是：

```text
实现登录功能
```

而应该是：

```text
Task: Implement login API client

Files:
- Modify src/api/auth.ts
- Add tests/auth.test.ts
- Do not modify UI
- Do not modify database schema

Inputs:
- POST /api/login
- body: { email, password }
- response: { token, user }

Requirements:
- use existing httpClient
- throw AuthError on 401
- return typed LoginResult
- include tests for success, 401, network error

Verification:
- npm test tests/auth.test.ts
- npm run typecheck

Escalation:
- If typecheck fails twice, produce bug dossier.
```

这叫“把智能压缩进规格”。

强模型越强，越应该被用来写这种合同。

# 7. Worker 失败时不能乱问老师，要标准化升级

我建议设置升级规则。

## Worker 自修上限

例如：

```text
DeepSeek Flash:
- 最多自修 1 次
- 超过直接问 DeepSeek Pro 或 Teacher

DeepSeek Pro / MiMo Pro:
- 最多自修 2 次
- 同类错误重复出现直接升级

Teacher:
- GPT/Gemini 只处理 bug dossier，不从头接管任务
```

避免弱模型无限循环浪费时间。

---

## Bug Dossier 标准

每次问老师必须带：

```text
1. Original task contract
2. Exact diff summary
3. Exact failing command
4. Exact error output
5. Attempts already tried
6. Suspected root cause
7. Relevant files only
8. Request: diagnose and produce minimal fix strategy
```

老师返回后，worker 执行。  
执行后 verifier 再验证。  
成功后 curator 沉淀 lesson。

# 8. 质量门：不能让 LLM 自己说完成

每个阶段必须有 gate。

## Preflight Gate

开始前检查：

- branch clean?
- correct worktree?
- dependencies installed?
- relevant rules loaded?
- no forbidden files touched?

---

## Build Gate

根据项目不同：

- Android: `./gradlew assembleDebug`
- Web: `npm run build`
- TS: `npm run typecheck`
- Python: `pytest`
- Chrome extension: manifest validation + build
- Server: unit tests + smoke API

---

## Runtime Gate

尤其你的 Android / mobile / extension 项目很需要：

- adb install
- app launch
- logcat crash check
- screenshot
- extension load check
- browser console check

---

## Spec Review Gate

强模型或 reviewer 检查：

- 是否满足 PRD/spec
- 是否越界
- 是否遗漏 i18n
- 是否违反设计铁律

---

## Code Quality Gate

检查：

- 资源泄露
- 线程安全
- 错误处理
- 类型安全
- 安全问题
- 可维护性
- 是否有 plausible but fake code

---

## Regression Gate

从历史失败案例库跑检查。

例如：

```bash
grep -rn "gradient" app/src
grep -rn "@clerk/clerk-expo" .
grep -rn "TODO" src
npm run typecheck
```

# 9. 自进化闭环应该长什么样？

每个任务结束后自动执行：

```text
1. What failed?
2. Why did it fail?
3. Which model failed?
4. Was the spec unclear?
5. Was the task too big?
6. Was the verifier missing?
7. Did teacher solve it?
8. What reusable lesson emerged?
9. Should we update:
   - project memory?
   - skill?
   - task template?
   - verifier script?
   - eval case?
   - model routing rule?
```

然后产出一个 `lesson packet`：

```yaml
lesson_id: voyager-clerk-direct-import
project: voyager-mobile
trigger: worker imported Clerk directly
root_cause: task contract did not include Clerk access rule
prevention:
  prompt_rule: Never import @clerk/clerk-expo directly
  verifier: grep -rn "@clerk/clerk-expo" .
  skill_patch: voyager-mobile-development
applies_to:
  - auth
  - mobile
  - Expo
  - Clerk
```

这就是能力迁移的基本单位。

# 13. 一个完整任务流示例

假设你说：

> Voyager mobile 需要加一个离线 Plan-B 修复功能。

系统应该这样跑：

## Step 1：Vision 扩展

GPT/Gemini 输出：

- 用户场景
- 为什么不是 itinerary planner
- offline survival 场景
- Plan-B repair 体验
- 风险

## Step 2：PRD

强模型写：

```text
Feature: Offline Plan-B Repair
Goal: 用户在旅途中断网/延误/地点关闭时，能快速获得替代方案
Non-goal: 不做完整行程规划
Acceptance:
- works offline with cached trip
- handles closed POI
- handles transport delay
- shows driver-safe local names when available
...
```

## Step 3：Spec

强模型写：

```text
Modules:
- OfflineTripCache
- PlanBRepairEngine
- RepairSuggestionCard
- API sync fallback
- i18n copy
```

## Step 4：Task Contracts

Planner 拆成：

```text
Task 1: Add OfflineTripCache model
Task 2: Add repair reason enum
Task 3: Add PlanBRepairEngine pure function
Task 4: Add UI card
Task 5: Add tests
Task 6: Add i18n zh/en
Task 7: Integration smoke
```

## Step 5：Worker 执行

- DeepSeek Flash 做 enum + tests
- MiMo Pro 做 UI
- DeepSeek Pro 做 engine
- Hermes parent 跑 build

## Step 6：失败升级

如果 MiMo UI 报错：


# 14. 这个系统真正的 RSI 点在哪里？

不是“AI 自己变成天才”，而是这几个闭环：

## 闭环 1：Spec 自我改进

Worker 失败说明 spec 不够清楚。  
Teacher 修复后，更新 spec template。  
下一次任务更清楚。

```text
失败 → 发现 spec 缺字段 → 更新 task template → 未来少失败
```

---

## 闭环 2：Verifier 自我扩展

Bug 漏掉说明 verifier 不够强。  
修复后加 regression check。

```text
bug → 新检测命令 → eval suite 增强 → 未来自动抓
```

---

## 闭环 3：Worker Prompt 自我进化

某模型常犯某类错误，就给它定制 prompt。

```text
DeepSeek Flash 常扩大范围
→ Flash worker prompt 加：Do not modify unrelated files
```

---

## 闭环 4：Teacher Knowledge 蒸馏

强模型救火后，把知识蒸馏给弱模型。

```text
GPT 诊断 → lesson → skill → weak worker context
```

---

## 闭环 5：Task Router 自我校准

记录每个模型在哪类任务成功率高。

```text
MiMo: UI success 82%, backend 55%
DeepSeek Pro: backend 88%, UI 60%
Flash: grep audit 95%, complex refactor 30%
```

以后自动分配任务。

# 15. 你应该避免的设计

## 不要让弱模型直接看你的原始创意就开干

会导致：

- 自己补需求
- 乱改架构
- 审美跑偏
- 做很多“看似完成”的东西

---

## 不要让老师直接包办所有任务

否则弱模型不会积累能力，系统也不会学会分工。

老师应该：

- 诊断
- 提供规则
- 修正 task template
- 帮助形成 lesson

---

## 不要把 LLM judge 当最终 verifier

LLM review 可以用，但最终要有：

- build
- test
- runtime
- screenshot
- grep
- formal checker
- real API response

---

## 不要只存 memory，不写 skills/evals

Memory 适合事实。  
Skill 适合流程。  
Eval 适合防复发。

三者要分开：

```text
memory: 项目稳定事实
skill: 可复用流程
eval: 自动检测脚本
```

# 17. 最终建议：你的系统名字可以叫 CELO

```text
Human Creativity

```

或者中文：

> 创意进化闭环系统
